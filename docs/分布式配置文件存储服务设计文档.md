# P2P 分布式配置文件存储服务设计文档
> 基于：Tauri 2.0 + EasyTier P2P 组网
> 目标：在已有的 P2P 虚拟局域网之上，实现轻量级分布式配置文件存储、请求、版本检查功能，供应用内各节点使用。

### 1. 需求背景与目标
#### 1.1 现状
应用通过 EasyTier 构建了 P2P 虚拟局域网，节点之间可以直接通信。

应用需要一套机制来统一管理和分发各类配置文件（如空间配置、网络策略、UI 偏好等）。

配置文件需要在局域网内可靠存储，支持版本控制和冲突避免。

#### 1.2 功能需求
需求项	描述
----
R1	节点可将配置文件存储到本地，并通过 P2P 网络提供给其他节点请求
R2	节点可向网络请求特定配置文件（按名称/ID）的最新版本
R3	配置文件附带版本号，支持版本检查（新版本通知或主动拉取）
R4	存储操作排队处理，使用文件锁保证写入一致性
R5	同一配置文件的连续多个存储请求，后到达的覆盖前一个（队列去重）
R6	支持版本校验（校验下载的文件完整性，可选）

#### 1.3 设计原则

去中心化：不依赖中心服务器，每个节点既是存储服务端也是客户端。

轻量级：基于 TCP 自定义协议或应用层 RPC，复用 EasyTier 提供的 IP 可达性。

简单可靠：避免分布式共识算法，通过文件锁 + 队列 + 覆盖策略解决并发问题。

### 2. 功能细节设计
#### 2.1 配置文件模型
```rust
struct ConfigFile {
    name: String,          // 逻辑名称，如 "space_settings"
    version: u32,          // 单调递增版本号
    content: Vec<u8>,      // 原始内容（可 JSON/TOML）
    timestamp: u64,        // 最后修改时间（Unix 毫秒）
    checksum: Option<String>, // 可选 SHA256
}
```
#### 2.2 存储节点模型
每个节点维护一个本地 configs/ 目录，按 {name}.json 存储文件。

伴随一个 versions.json 索引文件，记录本地每个配置文件的最新版本号和元数据，便于快速响应版本查询。

#### 2.3 请求/存储协议
基于 请求-响应 模式，使用 TCP 直连（端口可配置，默认 9877）。

协议消息类型 (JSON or Bincode)
```rust
enum Message {
    // 请求某个配置文件的最新版本信息
    QueryVersion { name: String },
    // 返回版本信息
    VersionInfo { name: String, version: u32, timestamp: u64, checksum: Option<String> },

    // 请求下载配置文件
    RequestFile { name: String, from_version: Option<u32> }, // from_version: 增量更新（预留）
    // 返回文件内容
    FileResponse { name: String, version: u32, content: Vec<u8>, checksum: Option<String> },

    // 存储配置文件到目标节点（推式更新）
    StoreFile { name: String, version: u32, content: Vec<u8>, timestamp: u64, checksum: Option<String> },
    // 存储结果
    StoreAck { name: String, success: bool, error: Option<String> },
}
```
#### 2.4 版本检查流程
节点 A 需获取 space_settings 的当前版本，向邻居节点广播或单播 QueryVersion。

节点 B 收到查询，读取本地 versions.json，若存在该配置则返回 VersionInfo，否则返回错误。

节点 A 比对本地版本，若远端更新，则发起 RequestFile 下载。

#### 2.5 存储队列与文件锁
每个节点内部维护一个 存储任务队列（内存 VecDeque 或 channel）。

队列采用 去重策略：以配置名称为键，若新提交的 StoreFile 的 name 已存在于队列中，则替换旧任务（保留最新版本和时间戳）。

后台一个 tokio 任务从队列中逐个取出任务执行存储。

存储过程：

对目标文件 configs/{name}.json 加上文件锁（使用 fs2 crate 的独占锁）。
写入内容，更新 versions.json（也需要锁保护）。
释放锁，返回 StoreAck。
#### 2.6 覆盖逻辑
在队列内：同一个 name 的存储请求，后来的直接替换先前的，保证只有最新操作会实际写入磁盘。

在写入前：写入时再次检查目标文件当前的版本，如果磁盘上的版本已经比待写入的版本高，可选择放弃写入或返回错误（默认放弃，避免回退）。

### 3. 架构设计

#### 3.1 模块层次
```text
core/
├── p2p/               # EasyTier 封装
├── config_store/
│   ├── store.rs       # 本地存储管理（读写、锁、版本索引）
│   ├── server.rs      # TCP 监听，处理远端请求
│   ├── client.rs      # 连接远端，发送请求
│   └── queue.rs       # 存储队列，去重逻辑
└── commands/          # 对外暴露的命令处理
```

#### 3.2 启动流程
应用启动，EasyTier 组网完成，获得 P2P 虚拟 IP。

启动 ConfigStoreService：

初始化本地存储目录。

启动 TCP 服务器（监听 0.0.0.0:9877）。

启动队列消费任务。

对外暴露命令 get_config_version, download_config, upload_config 等。

#### 3.3 节点发现
利用 EasyTier 提供的 网络广播/组播 或 分布式哈希表（DHT） 来发现对端节点的 IP 和端口。

简单实现：每个节点在加入网络后，通过 UDP 广播自己的服务端口，或维护一个已知节点列表（由空间管理提供）。

### 4. 关键流程
#### 4.1 请求配置文件（Pull）
```text
节点A                         节点B
  |                             |
  |---- QueryVersion(name) ---->|
  |<--- VersionInfo ------------|
  |                             |
  | (比较版本，若不同)
  |---- RequestFile(name,ver)->|
  |<--- FileResponse -----------|
  | (保存本地，更新索引)
```
#### 4.2 推送配置文件（Push）
适用于节点 A 主动将最新配置推送给节点 B：

```text
节点A                         节点B
  |                             |
  |---- StoreFile(data) ------->|
  |<--- StoreAck ---------------|
```
#### 4.3 本地存储队列处理
```text
[其他节点请求/本地触发] → 构造 StoreFile 任务 → 加入队列
队列消费循环:
  1. 取出任务 (去重后)
  2. 对文件加锁
  3. 比较磁盘版本与任务版本
  4. 写入文件
  5. 更新 versions.json
  6. 解锁
  7. 返回结果
```

```rust
// core/src/config_store/mod.rs
use serde::{Deserialize, Serialize};
use std::collections::HashMap;

#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct ConfigFileMeta {
    pub name: String,
    pub version: u32,
    pub timestamp: u64,
    pub checksum: Option<String>,
}

#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct ConfigFile {
    pub name: String,
    pub version: u32,
    pub content: Vec<u8>,
    pub timestamp: u64,
    pub checksum: Option<String>,
}

pub struct ConfigStore {
    root: std::path::PathBuf,
    versions: std::sync::RwLock<HashMap<String, ConfigFileMeta>>,
}
```
#### 5.3 文件存储与锁
```rust
impl ConfigStore {
    pub fn store(&self, file: ConfigFile) -> Result<(), StoreError> {
        let path = self.root.join(format!("{}.json", file.name));
        let lock_file = std::fs::File::create(path.with_extension("lock"))?;
        fs2::FileExt::lock_exclusive(&lock_file)?; // 加锁

        // 检查版本
        let current_meta = self.get_meta(&file.name);
        if let Some(meta) = current_meta {
            if meta.version >= file.version {
                // 放弃旧版本写入
                fs2::FileExt::unlock(&lock_file)?;
                return Err(StoreError::VersionConflict);
            }
        }

        // 写入内容
        std::fs::write(&path, &file.content)?;
        // 更新 versions.json
        self.update_versions(&file);

        fs2::FileExt::unlock(&lock_file)?;
        Ok(())
    }
}
```
#### 5.4 队列与去重
```rust
// core/src/config_store/queue.rs
use tokio::sync::mpsc;
use std::collections::HashMap;

pub struct StoreQueue {
    pending: HashMap<String, ConfigFile>, // name -> latest task
    sender: mpsc::UnboundedSender<ConfigFile>,
    receiver: mpsc::UnboundedReceiver<ConfigFile>,
}

impl StoreQueue {
    pub fn new() -> Self {
        let (tx, rx) = mpsc::unbounded_channel();
        Self { pending: HashMap::new(), sender: tx, receiver: rx }
    }

    pub fn submit(&mut self, file: ConfigFile) {
        // 覆盖队列中同名的旧任务
        self.pending.insert(file.name.clone(), file.clone());
        let _ = self.sender.send(file); // 实际发送，消费时会再次从 pending 取最新
    }

    pub async fn run(mut self, store: Arc<ConfigStore>) {
        while let Some(_task) = self.receiver.recv().await {
            // 处理时从 pending 中取出对应 name 的最新任务，避免重复处理被覆盖的
            let name = _task.name.clone();
            if let Some(actual) = self.pending.remove(&name) {
                if let Err(e) = store.store(actual) {
                    log::error!("Store failed: {:?}", e);
                }
            }
        }
    }
}
```
#### 5.5 网络通信
使用 tokio::net::TcpListener 监听，对每个连接解析 Message 枚举并分发。

简单序列化用 serde_json，高性能场景可换用 bincode。

客户端使用 tokio::net::TcpStream 连接对端 IP:9877。

#### 5.6 与桌面/服务器集成
核心逻辑在 core::config_store 实现。

桌面端和服务器端都可以通过 AppCommandHandler 暴露命令，如 get_remote_config_version, download_remote_config, push_config。

在桌面模式下，Tauri 命令直接调用 handler；在服务器模式下，HTTP 端点调用 handler。

### 6. 测试计划
单元测试：测试队列去重、文件锁冲突、版本比较。

集成测试：两个 EasyTier 节点之间请求/存储流程，验证版本同步。

压力测试：模拟多个节点同时推送同一配置文件，确保只有一个最新版本写入。

### 7. 部署与运维
无需额外部署，内嵌在应用二进制中，随应用启动。

可配置本地存储路径（APP_DATA/config_store）。

提供命令清除本地配置缓存。

通过以上设计，应用在 P2P 局域网内具备了分布式配置存储能力，版本管理、队列化和文件锁保证了数据的一致性和最新性，后续功能可在此基础之上继续扩展。
