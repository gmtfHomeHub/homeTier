Tauri 桌面应用 Linux 服务器化改造设计文档
适用项目：Rust + Tauri 2.0 + React + Vite 全平台应用
目标：在保持现有桌面端全功能的前提下，改造支持在 Linux 无图形服务器上运行，通过浏览器提供完整服务。
版本：v1.0

1. 背景与目标
1.1 现状
当前应用是一个基于 Tauri 2.0 的多平台桌面应用，覆盖 Windows、macOS、Android、iOS，包含以下核心功能：

编号	功能	优先级	依赖	当前平台
F1	P2P 虚拟局域网	P0	EasyTier	全平台
F2	空间管理	P0	F1	全平台
F3	P2P 聊天室	P0	F1	全平台
F4	文件共享	P1	F1	全平台
F5	实时语音	P1	-	全平台
F6	屏幕共享	P1	-	全平台
F7	快捷键控制	P1	F5,F6	桌面端
F8	聊天室隔离	P0	F1	全平台
F9	高级网络配置	P2	F1	全平台
F10	自动配置	P0	F1	全平台
F11	现代化 UI	P0	-	全平台
F12	三方 Web 应用	P0	-	全平台
前端使用 React + Vite，后端 Rust 通过 Tauri 命令与前端通信，并集成了 EasyTier 用于 P2P 组网。

1.2 需求
客户/场景要求将应用部署到 Linux 无图形服务器 上，使得用户可以通过 浏览器 访问所有功能，同时原有桌面版仍需完整保留。

1.3 改造目标
单代码库：桌面版与服务器版共享所有业务逻辑。

双模式运行：

桌面模式：Tauri 壳加载 React 前端，IPC 通信。

服务器模式：Axum/Actix-web 提供 HTTP 服务，浏览器访问 React 前端，REST/WebSocket 通信。

功能对齐：除平台强依赖功能（快捷键、原生对话框等）外，服务器版应提供与桌面版一致的用户体验。

平滑部署：服务器版能作为独立二进制运行，可通过 Docker/Systemd 管理。

2.2 通信抽象
核心思想：在 core 中定义 CommandHandler trait，桌面和服务器各自实现，前端通过统一适配层调用。

```rust
// core/src/commands.rs
#[async_trait]
pub trait AppCommandHandler: Send + Sync {
    // 示例命令
    async fn get_spaces(&self) -> Result<Vec<Space>, String>;
    async fn send_chat_message(&self, space_id: String, msg: ChatMessage) -> Result<(), String>;
    // ... 所有业务命令
}
```
- 桌面模式：实现该 trait，内部直接调用 core 中的函数，Tauri #[tauri::command] 函数将调用转发给该实现。

- 服务器模式：实现该 trait，Axum handler 调用该实现，前端通过 HTTP/WebSocket 发起请求。

2.3 前端适配层
提供统一的 apiClient，根据运行环境自动选择通信方式：

```typescript
// frontend/src/api/core.ts
const isDesktop = '__TAURI_INTERNALS__' in window;

export async function invoke<T>(cmd: string, args?: any): Promise<T> {
  if (isDesktop) {
    return window.__TAURI_INTERNALS__.invoke(cmd, args);
  } else {
    const res = await fetch(`/api/${cmd}`, {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify(args || {})
    });
    return res.json();
  }
}
```
WebSocket 通信也进行抽象，服务器端使用标准 WebSocket，桌面端可直接使用 Tauri 的事件系统或原生 WebSocket（如需要）。

2.4 功能分级支持策略
部分功能强依赖桌面环境，在服务器模式下需降级或替换：

功能	服务器模式处理方案
----
F5 实时语音	使用 WebRTC 浏览器端麦克风，信令经服务器中转；桌面端仍可使用原生音频捕获
F6 屏幕共享	浏览器端通过 getDisplayMedia 实现，桌面端保留原生屏幕捕获
F7 快捷键控制	服务器模式无系统级快捷键，改为页面内键盘事件或悬浮按钮
F12 三方 Web 代理	原自定义协议 proxy:// 改为 HTTP 反向代理路径，如 /proxy/encoded-url


3. 改造步骤
步骤 1：重构代码结构 —— 提取 core 库

1、创建 core/ 目录，将现有 src-tauri/src 中的纯业务逻辑移入：

- EasyTier 管理（启动、停止、节点信息）

- 聊天室消息处理

- 文件共享协调

- 语音/屏幕共享的信令与状态管理（抽象为 trait，不依赖具体平台）

- 第三方 Web 代理逻辑

2、定义 AppCommandHandler trait，将所有前端需要调用的功能抽象为方法。

3、将 core 作为 [lib] 编译，desktop 和 server 作为 [[bin]] 添加依赖。

步骤 2：重构桌面入口 (desktop/)

1、创建 desktop/，依赖 core 和 tauri。

2、实现 DesktopHandler 结构体，实现 AppCommandHandler，方法内部直接调用 core 中的函数。

3、将 Tauri 命令改为调用 handler：

```rust
#[tauri::command]
async fn get_spaces(state: State<'_, DesktopHandler>) -> Result<Vec<Space>, String> {
    state.get_spaces().await
}
```
4、保持现有 tauri.conf.json 及构建流程不变。

步骤 3：新增服务器入口 (server/)

1、创建 server/，依赖 core、axum、tokio、tower-http 等。

2、实现 ServerHandler 结构体，实现 AppCommandHandler。

3、编写路由，将每个命令映射为 HTTP POST 端点（或 RESTful 风格）：

```rust
Router::new()
    .route("/api/get_spaces", post(get_spaces))
    .route("/api/send_message", post(send_message))
```
4、添加 WebSocket 端点用于实时推送（聊天消息、状态更新），并在 handler 中集成 core 的事件总线。

5、提供静态文件服务，指向 frontend/dist 目录。

6、在 main.rs 中启动 HTTP 服务器，监听 0.0.0.0:3000。

步骤 4：改造 EasyTier 集成

EasyTier 是 P2P 组网基础，在服务器模式下需要以 库的形式 运行在后台线程，确保服务器节点也加入 P2P 网络。

- 在 core 中封装 EasyTier 生命周期管理，提供统一的启动/停止接口。

- 桌面和服务器均调用同一接口，因此组网能力一致。

步骤 5：前端改造

1、将原有 src-tauri 下的前端迁移到独立 frontend/ 目录（如尚未分离）。

2、修改 vite.config.ts，区分桌面和服务器构建：

- 桌面模式：保持 Tauri 环境变量，构建输出到 desktop/ 能访问的位置。

- 服务器模式：构建为普通 SPA，输出到 frontend/dist，由 server 静态托管。

3、实现 api/core.ts 通信适配层。

4、对屏幕共享、语音通话等功能，在服务器模式下使用浏览器原生 WebRTC API，并设计信令通过服务器 WebSocket 中转。

5、快捷键功能：服务器模式下移除全局快捷键依赖，改为页面内按钮或键盘监听（需焦点在页面内）。

步骤 6：第三方 Web 应用代理改造 (F12)

- 原方案在桌面端通过自定义 proxy:// 协议实现 iframe 代理，去除安全限制。

- 服务器模式下，改为服务器端提供 反向代理路由：

```rust
// 请求 /proxy?url=http://192.168.3.1:8081/...
async fn proxy_handler(Query(params): Query<HashMap<String, String>>) -> Response {
    let target = params.get("url")?;
    // 调用 core::proxy 模块，发起 HTTP 请求，清洗响应头，流式返回
}
```
- 前端 iframe 的 src 改为 /proxy?url=...，仍然能无缝嵌入任意内网 Web 页面。

步骤 7：构建与部署

1、桌面版构建：cargo tauri build（在 desktop/ 下执行）。

2、服务器版构建：

```bash
cd frontend && npm run build:server    # 输出到 frontend/dist
cd server && cargo build --release      # 二进制包含静态文件嵌入
```

- 推荐将 frontend/dist 通过 rust-embed 或 include_dir 编译进二进制，实现单文件部署。

- 提供 Dockerfile 和 docker-compose.yml 便于服务器部署。

4. 关键技术难点与解决
4.1 实时语音/屏幕共享的跨平台抽象

- 在 core 中定义 MediaCapture trait：

```rust
#[async_trait]
trait MediaCapture {
    async fn get_audio_stream(&self) -> Result<Stream, Err>;
    async fn get_display_stream(&self) -> Result<Stream, Err>;
}
```

- 桌面端实现：使用 tauri-plugin-webrtc 或原生捕捉。

- 服务器端实现：返回 None，由前端 JavaScript WebRTC API 自行获取媒体流，服务器仅负责信令。

4.2 快捷键 (F7) 的替代
服务器模式下，通过 Web 应用焦点内的键盘事件模拟快捷键，并设计一个浮动的快捷操作面板（OSD）来弥补无法全局监听的限制。

对移动端（Android/iOS）已有现成处理，可复用。

4.3 状态同步与多用户
服务器模式下可能多个用户同时访问，需注意 EasyTier 实例是全局唯一的，聊天室、空间管理等状态需正确共享（目前桌面版是单用户，服务器版仍需保持单用户逻辑？根据需求，可能是将服务器作为个人节点，通过浏览器远程访问，本质上仍是单用户，但允许多个浏览器标签页同时打开，需处理好状态一致性）。

5. 测试计划
单元测试：对 core 库编写完整测试，覆盖所有命令逻辑。

集成测试：分别测试桌面模式和服务器模式的基本功能。

端到端测试：使用 Playwright 测试服务器版 Web 界面。

性能测试：验证服务器模式下 EasyTier 组网延迟、文件共享吞吐量。

6. 注意事项
平台限制：部分功能在 Android/iOS 上本就有限制，服务器版同样继承这些限制。

安全：服务器模式会暴露网络端口，需加强认证（如 JWT、OAuth）和 TLS 加密，防止未授权访问。

EasyTier 许可：确认 EasyTier 在服务器端运行的合规性（通常开源允许）。

UI 适配：响应式设计确保在手机浏览器和桌面浏览器都能良好显示。

7. 结语
通过上述架构改造，你可以在保持现有全平台桌面应用不变的前提下，增加一个 Linux 服务器部署版本。用户只需通过浏览器即可远程访问原有的所有 P2P 协作功能，大幅扩展了产品的使用场景，尤其适用于不想安装客户端的临时用户或纯远程设备管理场景。

该方案最大程度复用了现有代码，且后续功能迭代只需在 core 中修改，两个版本同步更新，维护成本极低。
## 8. 子路径部署（nginx 反向代理子目录）

默认前端静态资源前缀为 `/`（桌面/移动端构建必须保持 `/`）。如需将服务器版部署到
nginx 子路径（如 `https://host/hometier/`），按以下步骤配置，**前端与后端前缀必须一致**。

### 8.1 前端构建（指定资源前缀）

```bash
# 复制模板并修改
cp .env.example .env
# 编辑 .env，设置 VITE_PUBLIC_BASE=/hometier/，然后：
pnpm build      # 产物 dist/index.html 中资源引用变为 /hometier/assets/...
```

未配置 `VITE_PUBLIC_BASE` 时默认 `/`，行为与改造前完全一致。

### 8.2 服务端配置（server.conf）

在服务器运行目录 `homeTier-data/server.conf`（由启动时自动生成）中设置：

```ini
SERVER_PUBLIC_BASE=/hometier/
```

`SERVER_PUBLIC_BASE` 默认 `/`。服务端按此前缀挂载静态资源，且认证放行逻辑
（`auth::is_static_resource`）会先剥前缀再判断，`/api/`、`/ws/` 仍受保护。

### 8.3 nginx 示例

```nginx
location /hometier/ {
    proxy_pass http://127.0.0.1:9339/;
    # 注意：若改为 proxy_pass http://127.0.0.1:9339;（不带尾斜杠）则需额外处理路径重写
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $remote_addr;
    # WebSocket
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
}
```

> 所有 `SERVER_*` 配置位于 `server.conf`（`SERVER_CONF_TEMPLATE`），与桌面 daemon 的
> `homeTier.conf` 相互独立。
